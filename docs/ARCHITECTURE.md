# 总体架构

## 1. 架构目标

首版部署为一台服务器、一个权威实时游戏进程和一个 SQLite 数据库。设计优先保证同房串行、规则可测试、资金原子性和私有信息隔离；不引入微服务、Redis、MySQL 或分布式共识。

## 2. 逻辑模块与依赖

```text
Vue Web ── HTTPS ──> HTTP/API ─────┐
   └───── WSS ────> Realtime/WS ──┼─> Application ─> Domain
Admin Web ─ HTTPS ─> Admin API ────┘         │           ▲
                                             v           │
                                      Infrastructure ────┘
                                      (SQLite, clock, RNG)
```

- **Domain**：牌、牌型、桌状态、动作合法性、状态机、底池构造、结算、领域命令/事件；纯 PHP，无 I/O。
- **Application**：房间/账号/钱包用例、事务边界、幂等键、授权策略、投影编排；依赖领域端口。
- **Infrastructure**：PDO 仓储、密码哈希、安全随机、系统时钟、审计和备份适配器。
- **Realtime**：Workerman 连接、房间邮箱、计时器、机器人调度、WS 协议；只调用应用用例。
- **HTTP**：登录、配置、管理、历史查询；不直接修改领域或数据库表。
- **Vue**：Pinia 保存服务端投影与本地 UI 状态，绝不自行裁决动作或结算。

依赖只能指向内层。Domain 定义 `RandomSource`、`Clock`、`IdGenerator` 等接口；生产适配器使用 `random_int`/安全洗牌与 UTC 时钟，测试适配器使用明确种子/脚本时间。生产配置不得接受固定牌堆或调试种子。

## 3. 权威牌局运行模型

每个房间有一个逻辑邮箱/命令队列；Workerman 单进程事件循环中同一房间一次只处理一个命令，不跨回调共享可变操作。不同房间可交错执行。首版若采用多个 worker，房间必须固定路由到唯一权威 worker；在实现并验证路由前，游戏 worker 数固定为 1。

处理流程：验证连接身份 → 检查 `request_id/hand_id/expected_version` → 加载房间状态 → 调用领域命令 → 原子持久化必要账目/事件 → 增加版本 → 按身份生成投影 → 广播。领域事件发布必须发生在提交成功后；失败不改变内存权威状态。

定时器不直接修改状态，只向同一邮箱提交带预期版本的 `ActionTimedOut` 或 `BotDecisionReady` 命令。暂停时记录剩余毫秒并取消计时器；恢复时以剩余值重建。旧计时器因版本不符成为无害过期命令。

## 4. 状态机

房间状态：`LOBBY -> WAITING_FOR_PLAYERS -> HAND_ACTIVE <-> PAUSED -> BETWEEN_HANDS -> CLOSED`。手牌状态：`POSTING_BLINDS -> PREFLOP -> FLOP -> TURN -> RIVER -> SHOWDOWN -> SETTLED`，也可从任一下注轮进入 `UNCONTESTED -> SETTLED`，或异常恢复进入 `VOIDED`。

命令表达意图（如 `JoinSeat`、`StartHand`、`Act`、`Disconnect`、`Pause`）；事件表达已发生事实（如 `PlayerSeated`、`HandStarted`、`ActionAccepted`、`PotAwarded`、`HandSettled`）。合法动作是服务端根据当前状态生成的值对象，包含动作类型、跟注额、最小/最大目标总下注额及是否会构成完整加注。

`state_version` 每个已接受房间事件批次递增；`hand_id` 在开手前生成；客户端 `request_id` 在会话主体范围唯一并保留去重结果。相同主体和 request_id 重试返回原结果，不重复执行；内容不同则返回冲突。

## 5. 数据与一致性边界

SQLite 是账号、永久 Player、钱包、正式桌托管、手牌检查点、结算、战绩和审计的最终事实源。实时内存状态负责低延迟，但不能成为永久筹码唯一记录。

- 普通房买入/追加/返还：一个数据库事务同时修改钱包、桌托管和不可变流水。
- 开手检查点：事务冻结参与者开手栈、配置快照和唯一 hand_id，标为 `STARTED`。
- 正常结算：以 hand_id 为幂等键，在一个事务内写底池/奖励、更新托管余额、战绩和 `SETTLED` 状态。
- 崩溃恢复：`STARTED` 且无结算提交的手恢复到开手检查点并记 `VOIDED`；`SETTLED` 不回滚、不重放。
- 对外事件采用“提交后发布”。如果客户端漏掉广播，通过版本检测和新快照恢复，不依赖消息恰好一次送达。

详细表与守恒式见 `DATABASE.md`。

## 6. 读模型与隐私投影

内部状态包含牌堆和所有底牌，严禁直接序列化。投影器接受观察者身份及当前阶段：

- 当前玩家：可见自己的底牌、公开牌和公开动作。
- 其他在座者/旁观者：仅见公共牌及已在摊牌中公开的底牌。
- 管理员：与其当前观察身份完全相同，不额外获得牌局秘密。
- 机器人策略：独立的 `BotDecisionContext`，只含自身私有信息和公开状态。

历史投影沿用“当时是否公开”的记录，不因管理员身份或牌局结束而解密弃牌。日志、异常和遥测只记录牌 ID 的不可逆诊断摘要或数量，不记录未公开牌面。

## 7. 房间、连接与恢复

HTTP 会话完成认证，WS 连接使用短时一次性连接票据。连接绑定 account/guest/player/room，服务端不信任客户端声明。重连携带上次已见版本；若事件缓存连续则补发，否则下发完整裁剪快照。

普通网络断线不销毁房间内状态。单真人桌自动暂停；多人桌继续计时并使用超时动作。进程崩溃属于不同故障域：启动恢复任务在接受新游戏流量前扫描未完成手牌，幂等作废并恢复检查点，然后安全关闭旧房间、返还托管余额。

## 8. 机器人扩展点

`BotStrategy::decide(BotDecisionContext): BotDecision` 返回动作意图，不直接修改桌状态。应用层在随机 1–3 秒后把意图作为普通 `Act` 命令提交；若版本变化则丢弃并重新评估。策略实现可替换，但首版只允许本地规则策略，不设计外部 AI 或训练管线。

## 9. 可观测性与运维

结构化日志包含 request_id、room_id、hand_id、state_version 和错误码，排除密码、会话令牌与私有牌。关键指标包括活跃连接/房间、命令延迟、非法/过期动作、SQLite busy、结算/恢复次数和守恒校验失败。守恒失败属于阻断性事件：停止受影响房间新开手并提示管理员检查，绝不自动补币。

## 10. 扩展边界

未来可拆分只通过现有端口进行：持久化适配器、策略适配器和连接层可以替换，领域规则不变。首版不为假想分布式场景引入消息总线、缓存集群、事件溯源平台或跨节点锁。
